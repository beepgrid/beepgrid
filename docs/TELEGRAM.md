# Telegram private bot channel

The native adapter supports private bot text messages, replies mapped to canonical conversations, administrator-linked immutable Person identities and versioned Approve/Deny buttons. Text replies are messages or clarifications, never implicit final decisions. Groups, forum topics, native file transfer and long polling are outside this release. Workspace files and other final responses require authenticated workspace continuation.

Use a dedicated bot that you control. Create a `telegram` connection with `config: {"bot_id":"12345","default_agent_id":"agent_id"}` and `secret` containing a JSON string with `bot_token` and `webhook_secret`. The token's numeric prefix must match `bot_id`; the webhook secret must have 16 to 256 characters from letters, numbers, underscore and hyphen. The bot identity is immutable for an existing installation. Only one enabled installation of a bot is allowed across workspaces in a database schema. Credentials are encrypted and absent from reads.

Read `GET /api/v1/connections/{id}/setup` for the exact callback. Inspect Telegram `getWebhookInfo` before registration. If another callback is registered, use a dedicated bot. Beep Grid does not register or delete provider webhooks. The operator registers the HTTPS callback with `secret_token`, `allowed_updates: ["message","callback_query"]` and `drop_pending_updates: false`. Webhook mode and `getUpdates` cannot run together. Do not drop pending updates during setup or recovery. These constraints follow the [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook).

Have the Person start the bot. A workspace administrator or appropriately delegated identity administrator attests `bot_id` and `user_id` with `POST /api/v1/people/{id}/telegram-account`. Linking does not grant contact or decision rights. Add a destination using the exact linked private user ID as `address`. Mutable usernames and group addresses are rejected. One linked bot/user pair per Person is supported in this release. `POST /api/v1/people/{id}/telegram-account/remove` unlinks it immediately.

Queue `POST /api/v1/connections/{id}/test` with `destination_id` and an `Idempotency-Key`. Read diagnostics. Provider acceptance leaves the state `verifying`; replying to that exact bot message can produce `connected` with `qualification: "engine_round_trip_observed"`. The evidence means the engine observed an authenticated correlated exchange. It does not attest independent human receipt, production readiness or business execution. Source fixtures use the same contract and are recorded separately from real-account qualification. SMTP requires independent mailbox receipt and authenticated continuation verification and cannot produce a native inbound-reply claim.

New unthreaded text starts a conversation with the configured default agent under the Person's current contact permissions. Reply to a mapped bot message to continue its conversation. Unknown reply targets are rejected. Every outgoing receipt and accepted inbound message is mapped independently, so later replies can address either. Each update ID is deduplicated atomically with its canonical mutation; out-of-order IDs remain processable. Reusing an ID with changed content is a conflict. Approval callback data is bounded to Telegram's 64-byte limit, includes the request version and must reference a message mapped to the same Person and conversation. Current audience, request state, action and decision policy remain authoritative.

Disable the installation using the normal versioned connection update to reject callbacks and queued sends. Relinking or unlinking a Person invalidates the old destination. Reconnecting a disabled bot requires a new webhook secret, registered by the operator, so old callbacks cannot revive authority. Rotate the bot token at Telegram separately if needed. Retry a known rate limit after the provider delay. A network loss, malformed success receipt or provider server failure produces an `unknown` send; reconcile it before replay, since Telegram does not provide a send idempotency key.

Protocol/race fixtures cover callback authentication, immutable linking, destinations, concurrent duplicates, changed duplicate IDs, out-of-order updates, canonical replies, versioned approvals, relink/unlink, disconnect/reconnect, credential rotation, rate limits and ambiguous sends. Live qualification still requires a designated authorized test bot, a reachable HTTPS callback and an attributed Person round trip plus approval and recovery/revoke evidence. No real bot has been registered or changed by this implementation.
